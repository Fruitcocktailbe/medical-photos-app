# Handoff — Medical Photos App → build repo

**For:** the Claude Code session in `D:\GithubLocal\medical-photos-app` (create the repo, copy this file to `docs/handoff-2026-10-03.md`). Full PRD: `J.A.R.V.I.S/projects/medical-photos-app/prd.md`. This file is the distilled build context; it does not repeat the PRD.

## What we are building

Android app (Expo dev build, TypeScript) for one user (Jeroen, plastic surgeon). Scan a patient label/sheet/screen → OCR name + DOB → pick visit type (+ region on the first visit; procedure set once per episode, later) → shoot a guided series with **live angle guidance** and automatic view tagging → files land in `<user-chosen folder>/Surname_Firstname_DOB/<episode>/YYYY-MM-DD_visit/` with EXIF/XMP tags, never in the camera roll. No backend.

## Decisions already made (do not reopen)

0. **Stack (decided 03/10, logged):** one Expo/React Native codebase for Android now and iOS later. Camera = `react-native-vision-camera` 5 (photo, barcode and face-detector outputs, live analysis on every frame); ML Kit on both platforms so geometry is identical across devices; OCR on a still via `@react-native-ml-kit/text-recognition`. Any community plugin that fails → our own thin native plugin in Kotlin + Swift.

1. Android first, Jeroen alone. iOS and multi-user later from the same codebase.
2. The patient's **name is read and used** (folder name `Surname_Firstname_YYYY-MM-DD`); file names are short (`20261003_preop_lat-L_01.jpg`). Barcode is read when present but is not the key.
3. Storage = **a folder the user picks or creates** via Android SAF (`ACTION_OPEN_DOCUMENT_TREE`). Second adapter: Google Drive REST API, only if the Drive app proves not to expose tree access. Interface: `StorageTarget { ensureFolder(path), writeFile(path, bytes, mime), verify(path, sha256) }`.
4. **Episode model.** Patient → episodes → sessions. An episode carries `region` (picked at the first visit, enough to choose the view set) and `procedure` (nullable; set once at surgery/first post-op, inherited by all sessions). **Pre-op never asks for the procedure.** Setting it later renames the episode folder and rewrites `session.json` + XMP of earlier images via the sync queue. Stored in `episode.json`, mirrored in `session.json`, folder name and XMP `dc:subject` (`procedure:<id>`, `view:<id>`, `visit:<id>`). Catalogue = bundled editable JSON (region → procedures → view set), starter list in PRD §6.
5. **Live angle guidance + auto view detection, on device.** ML Kit Face Detection yaw/pitch/roll per frame, face-box size for distance, box centre for framing; ML Kit Pose Detection shoulder line / torso for body; gyroscope for phone tilt. Target on a first visit = textbook angle; **on a follow-up = the capture geometry stored with the pre-op photo of that view** (saved in `session.json` and XMP). Green ring + arrows within tolerance (±5° face, ±8° body, defaults), optional auto-shutter. The same numbers tag the view; always one-tap override. Ghost overlay of the pre-op photo = **toggle**, remembered.
6. No cloud OCR, no cloud vision, no analytics on images, no Photos/MediaStore permission. Local copy wiped after verified write.
7. Before/after export (Phase 3) is in scope incl. aesthetic cases; gated by the per-patient "social" consent record; exports never carry prices or calls to action. Jeroen's call, logged.
8. **The folder is the database.** `patient.json` / `episode.json` / `session.json` hold all state; SQLite is a rebuildable cache. Reason: Jeroen's **tablet runs the same app in read-only viewer mode on the same root** to show pictures in the consult. v1: phone writes, tablet reads.
9. **Consent is oral**, given in the consultation. The app records it with one tap per patient (clinical / teaching / social, timestamp, who asked). No forms, no signatures, no consent PDF.
10. **Annotations:** one typed or dictated note per session (on-device speech recognition), and drawing on a **copy** of a photo (`<name>.annot.jpg`, same XMP). Originals are never modified.
11. **Capture happens anywhere** (consult, OR, ward, other clinics): handheld, no props, no fixed background. Lighting hints are soft nudges; normalisation is a Phase 2 post-process.
12. **Intra-op = free mode.** No step presets, no voice shutter.
13. **No reminders.** The app never schedules anything.
14. **Static only in v1**, but the data model must allow a view to be a short video clip and a view set to be an expression series (rest, brow raise, gentle/tight eye closure, smile, pucker, snarl) for facial palsy later. Do not hard-code "view = JPEG".
15. **Exports, in order after filing:** consult composite (phone + tablet) → social composite with the **personal mark "dr. Jeroen Poelaert + title"** (PNG + text line from settings) → teaching set builder with auto-anonymisation. EPD upload is not planned.
16. **Reporting later:** filter by procedure + interval, teaching sets (consent-filtered), personal outcome stats. Keep `episode.json`/`session.json` fields clean and typed for this.

## Constraints

- App-internal storage only; `FLAG_SECURE` on patient screens; biometric/PIN lock, 60 s auto-lock.
- Offline-first; write queue with retry and sha256 verification.
- Target device: Jeroen's Android phone (confirm model and Android version at kickoff; ML Kit needs API 21+, pose detection is heavier so test frame rate).
- Performance: identifier confirm screen < 5 s from pointing; guidance loop (face detect → ring update) < 100 ms per frame so it feels live; view tag from the same loop.
- Language of the UI: Dutch labels, English code.

## Open questions (answer during the spike, not before)

- OCR hit rate on Jeroen's real labels, handwritten sheets and agenda screens (20 samples each).
- Does the current Google Drive app accept `ACTION_OPEN_DOCUMENT_TREE`? If not, Drive API adapter or a locally synced folder.
- Pose-based body view classification: good enough to ship auto, or ship "assisted" (app proposes, user confirms) for breast/body in v1?
- Guidance ergonomics: can Jeroen hold the phone, read the ring and talk to the patient at once? Consider short voice cues ("iets meer naar links") as an option.
- Yaw accuracy of ML Kit on Jeroen's phone vs a protractor; decide the tolerance window from that, not from the spec.
- Handwriting: ML Kit Text Recognition v2 vs Digital Ink (needs stylus input, so probably no) → likely rely on the confirm screen.

## Suggested order

1. Repo skeleton: Expo dev build, `react-native-vision-camera` 5 + face-detector output, ML Kit text recognition, SAF folder target. Run on device. *(Done 03/10 in the spike build.)*
2. **Spike screens** (throwaway): (a) point at label → show parsed name/DOB; (b) live head-yaw/pitch/roll + face-box size readout with a target ring → does it feel usable?; (c) pick folder → write a test file → rename a folder → read it back.
3. MVP slice 1: identify → confirm → free-mode shoot → file to folder with names + XMP. This alone already removes the camera-roll problem; use it in clinic from here.
4. Slice 2: episode model (region first, procedure later with backfill) + visit types + guided views with live angle guidance and auto tag; store capture geometry per photo.
5. Slice 3: ghost overlay toggle, browse screen, consent record, session note + dictation, drawing-on-copy, app lock, audit log, **index rebuild from folder** + tablet viewer mode.
6. Pilot 4 weeks. Add the app to `J.A.R.V.I.S/references/live-site-security-checklist.md` status table before the first real patient.
